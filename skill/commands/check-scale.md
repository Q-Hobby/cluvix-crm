## Iron Law

**KHÔNG kết luận hiệu năng từ DB dev.** Dev có vài trăm dòng → mọi endpoint trả 7ms và che sạch
đường đi mất 6.8 giây ở 500k dòng. Mọi phán quyết "đã nhanh" / "không có vấn đề" phải dựa trên số
đo ở quy mô, hoặc không được phát biểu.

Hệ quả: lệnh nào kết luận bằng một con số thì phải kèm **dòng đối chứng** chứng minh phép đo có
chạy thật (`SELECT 1`, hoặc một mẫu chắc chắn có hit).

## Bước 1 — Tách SQL khỏi Go trước khi đoán bất cứ điều gì

Đọc `backend/tmp/run.log`. `pkg/logger/gorm.go` in `[SLOW SQL <t>] @ <path>` cho mọi query ≥200ms.

- Tổng thời gian request − tổng SLOW SQL = phần của code Go.
- Một câu SQL chiếm ~100% thời gian ⇒ vấn đề ở DB, **không đọc code Go tìm N+1 nữa**.
- Nhiều câu nhỏ lặp lại ⇒ N+1, vấn đề ở Go.
- Không có dòng SLOW SQL nào ⇒ hoặc thật sự nhanh ở quy mô hiện tại, hoặc chưa ai bấm vào nó —
  **không kết luận, sang Bước 2**.

⚠ Không có log ≠ không có vấn đề. Ngưỡng là 200ms; ở dev một query 6.8s-tại-500k chỉ tốn 7ms.

## Bước 2 — Dựng bench ở quy mô

1. Clone schema THẬT — `mysqldump --no-data`, KHÔNG tự gõ lại `CREATE TABLE`.
   Bảng tự gõ luôn permissive hơn thật; đã có tiền lệ loại nhầm một giả thuyết đúng suốt 9 ngày
   vì bench dùng bảng cha tự gõ.
2. Tên DB **bắt buộc** kết thúc `_test` hoặc `_tmp`. TUYỆT ĐỐI không trỏ vào `DB_NAME` trong `.env`.
3. Sinh **≥500k dòng** bằng bảng số nhân đôi:
   ```sql
   CREATE TABLE nums(n INT PRIMARY KEY); INSERT INTO nums VALUES (1);
   -- lặp ~19 lần:
   SET @m := (SELECT MAX(n) FROM nums); INSERT INTO nums SELECT n + @m FROM nums;
   ```
   Rồi `INSERT … SELECT … FROM nums` với `SET FOREIGN_KEY_CHECKS=0; SET UNIQUE_CHECKS=0;`.
   Dữ liệu phải **giống thật ở chỗ có ý nghĩa** — tên tiếng Việt thật nếu đo tìm kiếm, ngày trải
   đều nếu đo lọc theo ngày.

## Bước 3 — Đo 5 ca, không chỉ ca đẹp

| Ca | Vì sao bắt buộc |
|---|---|
| Filter hẹp (1 ngày) | đường nhanh nhất — mốc so sánh |
| KHÔNG filter | mặc định của nhiều màn |
| Phân trang sâu (`OFFSET` lớn) | chi phí `OFFSET` tuyến tính |
| Từ khoá CÓ khớp | |
| **Từ khoá KHÔNG khớp / hiếm** | **ca xấu nhất, hay bị bỏ sót** — `SELECT` thoát sớm khi đủ `LIMIT` nhưng `COUNT` của pagination KHÔNG BAO GIỜ thoát sớm được |

Luật đo:
- Luôn có dòng `SELECT 1` để trừ overhead kết nối (~40ms với `mysql` client).
- Chạy mỗi biến thể **≥2 lần** — lần đầu là cache lạnh, đừng kết luận trên nó.
- Đo riêng `SELECT` và `COUNT`. `pagination.Paginate` chạy `COUNT(*) FROM (SELECT … ORDER BY)` bọc
  NGUYÊN query ⇒ mọi chi phí join/filter bị trả **hai lần** mỗi lần load.
- `EXPLAIN` để xác nhận cơ chế, nhưng `EXPLAIN` trên DB dev vô nghĩa (vài trăm dòng → optimizer
  luôn chọn full scan).

## Bước 4 — Thử biến thể sửa, ghi lại cả cái bị loại

Mỗi biến thể: đo, ghi số, giữ hoặc loại. **Biến thể bị loại phải được ghi kèm số đo** vào comment
code hoặc header migration — nếu không, session sau sẽ thử lại đúng cái đó.

Nút thắt đã biết và cách chữa đã đo — đọc
`skill/skills/debugging-backend-queries/reference/perf-list-endpoints.md` trước khi tự nghĩ ra cách mới:
- `LEFT JOIN` vô điều kiện (MySQL không loại-bỏ-left-join)
- `LIKE '%kw%'` xuyên join
- `COUNT(*)` derived của `Paginate`
- FK con làm chậm UPDATE bảng cha (~5ms/FK)
- Index thừa kiểu tiền-tố-trái

**Gate trước khi ship một index: ép dùng chính nó.** Đo 3 cách trên cùng câu query —
(a) không có index, (b) có index, để optimizer tự chọn, (c) có index + `FORCE INDEX (<index đó>)`.
Nếu (c) **chậm hơn** (b) thì phần thắng KHÔNG đến từ index: nó chỉ làm cost model đổi sang một plan
khác, và sẽ lật ngược khi phân bố dữ liệu đổi ⇒ **KHÔNG ship**. Đọc `EXPLAIN` của (b) xem optimizer
thật ra đang dùng gì. Ca thật: index `(customer_id, company_id)` cho COUNT 2,71–5,28s → 0,27–1,18s,
nhưng ép dùng chính nó = 0,67–0,97s và `EXPLAIN` (b) hoá ra là `Index scan on PRIMARY (reverse)` —
đã loại.
